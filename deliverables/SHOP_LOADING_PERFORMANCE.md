# 상품구매 화면 로딩 성능 개선

## 적용 범위

- 사용자 대시보드의 `상품 구매` 버튼에서 `/shop`으로 이동하는 구간
- 상품·디자인 목록, 보호자 배송지, 관리대상, 사용 가능 쿠폰 조회
- 상품 썸네일과 디자인 썸네일·상세 이미지 제공

## 확인된 원인

- 기존 `getProducts()`는 상품과 디자인의 Base64 원본 이미지를 `/shop` 서버 컴포넌트 데이터에 모두 포함했다.
- 운영 데이터 기준 인라인 이미지 크기는 약 3.3MB였으며 상품과 디자인 조회에 각각 약 1.1초, 1.4초가 걸렸다.
- 쿠폰 조회가 내부에서 보호자 대시보드 조회를 다시 호출하여 보호자와 공통 설정을 중복 조회했다.
- 서버 응답이 끝날 때까지 별도 로딩 화면이 없어 사용자는 버튼이 반응하지 않는 것으로 느낄 수 있었다.

## 반영 내용

- `getShopProducts()`는 이름, 가격, 정렬, 이미지 존재 여부와 갱신시각만 조회한다.
- 상품과 디자인 메타데이터를 독립된 두 SQL 문으로 구성하고 Turso batch 한 번으로 실행한다.
- `getShopPageData()`는 보호자, 최소 관리대상 필드, 쿠폰을 Turso batch 한 번으로 조회한다.
- 상품·디자인 원본 이미지는 아래 전용 URL에서 화면에 필요한 시점에만 제공한다.
  - `/api/products/[id]/image`
  - `/api/products/[id]/detail`
  - `/api/products/designs/[id]/image`
  - `/api/products/designs/[id]/detail`
- 이미지 URL에는 레코드 갱신시각을 버전값으로 붙이고, 응답은 장기 브라우저 캐시를 사용한다.
- `/shop/loading.js`를 추가하여 페이지 이동 즉시 상품 로딩 상태를 표시한다.

## 계측 결과

- 변경 전 상품·디자인 인라인 이미지: 약 3.3MB
- 변경 후 상품·디자인 초기 메타데이터: 약 33KB
- 운영 Turso 직접 계측: 약 2.5초의 이미지 포함 조회에서 약 0.44초의 메타데이터 배치 조회로 감소
- 로컬 이미지 API: 상품 썸네일과 디자인 썸네일 모두 HTTP 200 확인

계측값은 네트워크와 Vercel 함수 상태에 따라 달라질 수 있다. 핵심 기준은 `/shop` 초기 응답에 `image_data_url`, `option_image_data_url`, `detail_image_data_url` 원문을 포함하지 않는 것이다.

## 유지보수 기준

- 상품 선택 첫 화면에는 원본 Base64 이미지를 서버 컴포넌트 props로 전달하지 않는다.
- 새 이미지 종류가 추가되면 메타데이터에는 존재 여부와 버전만 추가하고 별도 이미지 Route Handler를 사용한다.
- 이미지 Route Handler는 MIME 서명 검증, `nosniff`, 샌드박스 CSP를 유지한다.
- 결제 요청의 상품 ID, 디자인 ID, 가격 검증은 기존 서버 로직을 계속 사용한다.
